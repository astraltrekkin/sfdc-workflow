# WRK PR

Write the PR **title** and **body** for the current local work. Hand them to
the user (or include them in the remote final report). Stop.

## Hard rules

- **DO NOT push** to any remote.
- **DO NOT** run `gh pr create`, open a PR, or post on GitHub.
- **DO NOT** commit unless the user separately asks.
- **DO NOT write "Made with Cursor"** (or any similar Cursor attribution /
  marketing footer) anywhere in the PR title, PR body, commit message
  suggestions, or commentary. If a tool or template inserts it, remove it
  before delivery.
- **NEVER** add any co-author / agent attribution anywhere in the title, body,
  commit message suggestions, or commentary. Forbidden examples include (not
  exhaustive):
  - `Co-Authored-By: …`
  - `Co-authored-by: …`
  - Cursor / Claude / Copilot / GPT / any model or bot as
    co-author
  - "Made with Cursor", "Generated by…", "Assisted by…" footers
- If a tool or template would insert any of the above, strip it before delivery.
- **NEVER** put internal/fork plumbing in the PR title or body. The PR reads as
  a normal upstream contribution. Do **not** mention:
  - fork owner / fork URL (e.g. `fork-owner/…`)
  - agent branch names (`cursor/…`)
  - "not opened as PR", "draft only", "wrk-e2e"
  - where the work lived before opening the PR
  Branch/fork details belong only in a separate note to the operator outside
  the pasteable PR body (or omit entirely).
- **NEVER** put WRK / suite / agent **pipeline meta-language** in the PR
  title or body. Upstream reviewers must not see how the work was produced.
  Forbidden in any section (including **Screenshots / Logs**, How to Test,
  Checklist, and N/A fillers), not exhaustive:
  - Codex / "live Codex run" / Claude / Cursor / GPT as process
  - `wrk-e2e`, `wrk-begin`, `wrk-bug`, `wrk-pr`, "this path", "unit coverage only"
  - "does not require an API key" / "no API key" as a substitute for evidence
  - "N/A — …" excuses that narrate the automation (e.g.
    `N/A — unit coverage only; no live Codex run (this path does not require an API key).`)
  If a section needs evidence and you have none: leave it blank, keep the
  template placeholder, or write a short **user-facing** note (e.g. test
  command output). Do **not** invent WRK-suite rationale.
- **If a checkout PR template exists, you MUST fill that file in place.** Do
  not invent a parallel skeleton. Do not use `fallback_template.md` when a
  checkout template is present. Keep heading text and checkbox labels
  (including emojis) exactly as in the template.

## When chained from wrk-e2e

- Run this skill only if the recap **Successful repro** checkbox is `- [x] Yes`.
- If Successful repro is No, or status is `repro_failed` / `hard_stop`, **skip**
  this skill.
- Skill file lives in the attached suite checkout:
  `.cursor/skills/wrk-pr/SKILL.md` (search under the multi-repo workspace if
  the primary cwd is the fork).
- Still **do not** open a GitHub PR (`gh pr create`). Draft text only.
- **Do** sync/rebase onto the upstream PR base and push the updated
  `cursor/...` branch to the **fork** when the sync step requires it.

## Steps

1. **Sync to PR base (required, before drafting)** — Hard gate. From the
   **primary work repo** (fork checkout), the branch must not be behind the
   branch the PR will target. Run:

   ```bash
   $CTL check-pr-base
   # or: python3 …/wrk-e2e/scripts/ctl.py check-pr-base --issue owner/repo#N
   ```

   This fetches upstream, Sync-forks / rebases if needed, and **exits non-zero**
   if still `behind > 0` or rebase conflicts (`STATUS: hard_stop` + recovery
   commands). Do **not** draft a PR if it fails.

   Manual equivalent (same rules as the gate):

   1. Resolve **PR base** (repo-agnostic):
      - Prefer an explicit base named in `.github/PULL_REQUEST_TEMPLATE.md`
        (e.g. “PRs must target the `dev` branch” → `dev`).
      - Else use the upstream default branch (`main` / `master` / …).
   2. Ensure remotes: `upstream` = upstream repo, `origin` = fork.
   3. `git fetch upstream` (and `origin` if needed).
   4. Measure: `BEHIND=$(git rev-list --count HEAD..upstream/<base>)`
   5. If `BEHIND` > 0: rebase (preferred) or merge onto `upstream/<base>`,
      resolve conflicts, re-run relevant tests if the rebase touched the fix.
      Push the updated agent branch to the **fork only**
      (`git push --force-with-lease origin HEAD` when history rewrote).
   6. Re-check until `BEHIND` is `0`. Record in the report:
      `base=<name> behind=0 ahead=<n>`.
   7. If rebase onto the required base is impossible (wrong root / diverged
      histories): stop, report `STATUS: hard_stop` with why — do **not**
      draft a PR against the wrong base.

   Override (discouraged): `WRK_ALLOW_BEHIND_UPSTREAM=1`.

2. **Ground truth** — Still on the synced branch:
   - `git status --short`, `git branch --show-current`
   - Diff vs PR base: `git diff upstream/<base>...HEAD` (plus unstaged if any)
   - Related issue URL/number from branch name, conversation, or user

3. **Resolve template (required shell step)** — from the **fork checkout**:

   ```bash
   TEMPLATE=""
   for p in \
     .github/PULL_REQUEST_TEMPLATE.md \
     PULL_REQUEST_TEMPLATE.md \
     .github/PULL_REQUEST_TEMPLATE/pull_request_template.md
   do
     if [ -f "$p" ]; then TEMPLATE="$p"; break; fi
   done
   if [ -z "$TEMPLATE" ] && [ -d .github/PULL_REQUEST_TEMPLATE ]; then
     TEMPLATE="$(find .github/PULL_REQUEST_TEMPLATE -maxdepth 1 -name '*.md' | head -1)"
   fi
   if [ -n "$TEMPLATE" ]; then
     echo "template=checkout:$TEMPLATE"
     # Read THIS file. Fill it in place. Do not open fallback_template.md.
   else
     SKILL_ROOT="$(find . -path '*/.cursor/skills/wrk-pr/fallback_template.md' 2>/dev/null | head -1 | xargs dirname)"
     TEMPLATE="$SKILL_ROOT/fallback_template.md"
     echo "template=fallback:$TEMPLATE"
   fi
   ```

   Copy the resolved template into your draft buffer and fill sections. Keep
   every required `##` / `###` heading text identical (emojis included). Keep
   every checkbox **label** identical (e.g. `🐛 Bug fix (…)`) — only flip
   `[ ]` ↔ `[x]`. Delete whole optional sections only when the template HTML
   comment says to (e.g. “For New Skills — Delete this section otherwise”).

4. **Fill every section** from the real diff and issue. Be concrete (paths,
   repro, expected/actual). Check the correct **Type of Change** box.
   Mark checklist items honestly from what was actually done; leave unchecked
   what was not verified. Strip HTML comments from the delivered body.

   **Screenshots / Logs** (or similarly named section) — only when the template
   has this section. Decide **Yes / No** before writing anything:

   | Question | If **No** | If **Yes** |
   |---|---|---|
   | Is there evidence that **relates to this change / build**? | Keep the section **empty**. Do not invent fillers. | Continue. |
   | Is that evidence available to paste (screenshot link, log excerpt, build/test output for this fix)? | Keep the section **empty**. | Paste **only** that related evidence. |

   Rules when filling (**Yes** path):

   - Include **only** material that relates to this PR’s build / fix / repro
     (e.g. failing then passing output for the changed behavior, UI screenshot
     of the bug/fix, CI log lines for the job that exercised this change).
   - **Do not** add unrelated information — e.g. dry generic unit-test tallies
     (`1 passed, 2 failed`) that are not about this build, noise from other
     packages, or drive-by suite summaries.
   - Never fill with pipeline meta (`Codex`, `wrk-e2e`, "unit coverage only",
     "this path does not require an API key", etc.).
   - Prefer empty over padding.

5. **Suggested title** — Conventional Commits, matching the repo
   (`fix(scope): …`, `feat(scope): …`, etc.).

6. **Gate (required)** — before delivery, run the checker. When
   `template=checkout:…`, pass `--template-file` so the fingerprint gate runs.

   ```bash
   SKILL_ROOT="$(find . -path '*/.cursor/skills/wrk-pr/scripts/check_pr_text.py' 2>/dev/null | head -1 | xargs dirname | xargs dirname)"
   : "${SKILL_ROOT:=$(cd "$(dirname "$0")/.." 2>/dev/null && pwd)}"

   # TEMPLATE is the path from step 3
   if [ -n "$TEMPLATE" ] && [ -f "$TEMPLATE" ]; then
     python3 "$SKILL_ROOT/scripts/check_pr_text.py" \
       --title "$PR_TITLE" \
       --body "$PR_BODY" \
       --template-file "$TEMPLATE"
   else
     python3 "$SKILL_ROOT/scripts/check_pr_text.py" \
       --title "$PR_TITLE" \
       --body "$PR_BODY"
   fi
   ```

   Exit code must be `0`. Re-draft until it passes. Never deliver a failing draft.

7. **Deliver** — Output only:
   1. Suggested PR title (one line)
   2. Full PR body in a single markdown code block, ready to paste
   3. Sync line: `base=<name> behind=0 ahead=<n>` (required)
   4. Template line: `template=checkout:<path>` or `template=fallback:<path>` (required)
   5. One-line note: no GitHub PR was opened (`gh pr create` not run)
   6. Confirm: `wrk-pr check OK`

Do not create the PR. Stop after delivery.

## Fallback template location

Only when step 3 finds **no** checkout template:

`.cursor/skills/wrk-pr/fallback_template.md`

Do **not** open that file if a checkout template exists.

# WRK Reviewer Ono

Investigate a person who reviewed or commented on a GitHub issue/PR. Produce a
structured report and style it as HENRY HTML. Deliver in-chat; write HTML only
if the user asks.

**Do not change product code** unless the user separately asks. This skill is
investigate → report.

## Inputs

From the user (or ambient PR/issue context), obtain:

| Input | Required | Notes |
|---|---|---|
| Issue or PR URL / number + repo | yes* | e.g. `owner/repo#123` — this sets the target repo for all sweeps |
| Commenter handle or comment URL | no† | who to vet — **infer, do not block** |
| Extra focus | no | e.g. “only the bot-admission claim” |

\* If the issue/PR is missing, pull it from ambient chat / open tabs / recent
`gh` context first. Ask only if still impossible after that — **one short ask,
then wait**. Never stall with “I’ll ask before proceeding” as a substitute for
looking.

† **Commenter handle is not a stop.** Never refuse or pause the run because the
user omitted `@handle`. Infer it automatically, in order:

1. Explicit handle / comment URL / review URL in the user message
2. Ambient chat (prior turns naming a reviewer/commenter)
3. Load the issue/PR and pick the target:
   - latest **review** (PR) or latest **issue/PR comment** that is not the
     issue/PR author
   - prefer human reviewers over bots when both exist; if the user’s focus is a
     bot claim, use that bot
4. If several humans commented, prefer the most recent substantive review/comment
   (not “LGTM”/emoji-only if a longer comment exists nearby)

State the inferred handle in one line (`Vetting @handle from <url>`) and
**continue**. Ask only when inference is truly ambiguous (two equally plausible
targets) — one question, otherwise proceed with the best guess and note it.

## Deliverable

In-chat report is required. HTML file is optional (ask once after the report).
Do **not** send mail or call any mail MCP.

## Workflow checklist

Copy and track:

```
WRK Reviewer Ono
- [ ] 1. Load target issue/PR + the comment/review
- [ ] 2. Section 1 — issue recap (≤150 words, bullets)

```

## Step 1 — Gather source material

Use `gh` and/or GitHub MCP:

1. Issue/PR title, body, labels, state, linked issues.
2. The target comment or review (full body, timestamps, `author_association`).
3. Nearby thread context only if needed to interpret the claim.
4. Confirm local checkout matches the PR head when validating code claims
   (see wrk-rev-com step 1).

---

## Step 2 — Report sections (content)

Build these five content blocks before designing the email.

### 1. Recap what issue is

- Up to **150 words total**, in **bullets only**.
- Cover: problem, requested behavior, current status of the PR/issue.
- No fluff; no pasting the whole issue body.

### 2. What the reviewer is saying

- Quote or paraphrase tightly.
- Number distinct asks / claims.
- Note if the comment is human review vs automated triage / bot boilerplate
  (e.g. “generated by AI during triage”, graph/sweeper bots, identical footers).

### 3. Is it legitimate?

**Employ the wrk-rev-com skill/command.** Read and follow:

- Prefer: `~/.cursor/commands/wrk-rev-com.md`
- Fallback: `~/.claude/commands/wrk-rev-com.md`

Run its full validation sequence (branch check → extract claims → classify →
validate with evidence → recommend accept / push back / clarify / no-op).

In the email, summarize:

- Overall legitimacy: **legitimate** / **partially legitimate** / **not legitimate** / **unclear**
- What you checked (files, helpers, tests, `author_association`, prior maintainer asks)
- Per-claim table or bullets with **confirmed / partially true / incorrect / unclear**
- Recommended action for the contributor (not “thanks”, no filler)

### 4. Who is the commenter?

Profile sweep (use `gh api`, GitHub MCP, web as needed):

- GitHub login, name, bio, company, location, account age
- **Avatar URL** — from `avatar_url` on the user/bot (`gh api users/HANDLE` or
  the comment/review payload). Required for the email (see profile image below).
- `author_association` on this comment
- Org membership signals (public member of the issue/PR’s `OWNER` org?
  collaborator? none?)
- Bot / automation signals (`type: Bot`, `[bot]` login, GitHub App actor,
  identical AI triage footers, graph/sweeper HTML comments, thousands of
  near-identical posts)
- Short recap: who they appear to be in 3–6 bullets

#### Required identity lines (always)

Always include these two lines verbatim in section 03 (and in `{{META}}` /
`{{STANDFIRST}}` / chat reply):

```
Is maintainer: yes
Is bot: no
```

or the matching `no` / `yes` values. **Never omit either line.**

- **`Is maintainer:`** — same verdict as repo-maintainer heuristics below
  (`yes` only with strong evidence; otherwise `no`). Alias line still required:
  also keep `Repo maintainer: yes|no` immediately under these two lines
  (same value as `Is maintainer`).
- **`Is bot:`** — `yes` if GitHub `type` is `Bot`, login ends with `[bot]`, or the
  actor is a GitHub App / automation poster; otherwise `no`. Prefer evidence over
  guesswork (API `type`, app slug, repeated boilerplate).

#### Profile image (required in the email)

Embed the commenter’s GitHub profile image in **`{{SECTION_3_BODY}}`**, at the
**top** of the who-section (before profile bullets):

1. Fetch `avatar_url` (prefer `?s=160` or similar sized variant).
2. Prefer a **resized data-URI** (`data:image/png;base64,…` or jpeg/webp) for
   reliability; absolute `https://avatars.githubusercontent.com/…` is
   acceptable if fetch/resize fails.
3. Markup (inline-table nested table cell; keep ~64–80px):

```html
<img data-ono-avatar="1" src="data:image/png;base64,…" width="72" height="72" alt="@handle"
  style="display:block;width:72px;height:72px;border:0;border-radius:36px;" />
```

4. **Exactly one** `data-ono-avatar="1"` image. Do **not** set
   `data-henry-element` on it (assert treats it separately from Henry kit imgs).
5. Caption under the avatar (mono, muted): `@handle · GitHub avatar`.

#### Target-repo activity sweep (required)

Derive `OWNER/REPO` from the issue/PR under review (never hardcode a product
repo). Always run a **repo-scoped** activity sweep on that `OWNER/REPO` for this
handle. Recap it in section 03 (totals + pattern), then render as a
**GitHub-style contribution pixel grid** in the email.

Collect (prefer `gh`; parallelize; substitute the real `OWNER/REPO`):

| Signal | How |
|---|---|
| Issues/PRs authored | `gh api "search/issues?q=repo:OWNER/REPO+author:HANDLE"` → `total_count` |
| Issues/PRs commented | `…+commenter:HANDLE` → `total_count` |
| PRs reviewed | `…+reviewed-by:HANDLE` → `total_count` |
| Open authored PRs | optional filter `is:pr+is:open+author:HANDLE` |
| Day-level events (for the grid) | `gh api "users/HANDLE/events?per_page=100"` paginate up to ~3–10 pages; keep only events where `repo.name == "OWNER/REPO"`; count by UTC date. If events are sparse, also sample recent search hits (`created:YYYY-MM-DD` windows) for comments/PRs to densify the last ~12 months. |

Activity recap bullets (2–5):

- Totals: authored / commented / reviewed on `OWNER/REPO`
- Cadence: bursty automation vs human sparse vs maintainer-steady
- Dominant action type (triage comments, reviews, code PRs)
- Oldest/newest touch on this repo you observed (if available)

**Pixel grid (required in the email):**

- Shape: last **52 weeks × 7 days** (Sun→Sat rows or Mon→Sun — pick one and
  stay consistent), GitHub contribution-graph layout (weeks as columns).
- Each cell = one day; fill level from that day’s event count on `OWNER/REPO`.
- Levels (map counts → color; use nested `<table>` cells, not CSS grid — inline-table):

  | Level | Count (tune if needed) | Fill |
  |---|---|---|
  | 0 | 0 | `#161b22` (empty, on dark panel) |
  | 1 | 1–2 | `#0e4429` |
  | 2 | 3–5 | `#006d32` |
  | 3 | 6–10 | `#26a641` |
  | 4 | 11+ | `#39d353` |

- Cell size ~10–12px square, 2px gap (padding on `td` or spacer cells).
- Caption under the grid:
  `<repo-name> activity · last 12 months · N events observed`
  (use the repo short name, e.g. `qdrant` from `qdrant/qdrant`)
  plus a 5-swatch legend (Less → More).
- If the events API returns almost nothing, still draw the full empty grid and
  state that limitation in the caption (do not fake density).

Insert the grid HTML into the Henry email’s who-section body
(`{{SECTION_3_BODY}}` — after profile bullets + identity lines, before the
closing identity block if you place identity after the grid). Keep inline-table
nested tables (or a compact pre grid if payload size forces it); never drop the
activity block.

Helper (preferred): pipe day counts JSON into
`scripts/build_activity_grid.py --repo REPO` — stdout is the grid HTML; stderr
is the caption line to append under the grid (`REPO` = short repo name).

**Section 03 closing identity block (required, in this order):**

```
Is maintainer: yes|no
Is bot: yes|no
Repo maintainer: yes|no
```

Heuristics for **Is maintainer: yes** / **Repo maintainer: yes** (need strong
evidence — both lines must match):

- Known core maintainers of `OWNER/REPO` (e.g. requested reviewers with merge
  authority), **or**
- `OWNER` / `MEMBER` association on this issue/PR **and** sustained
  maintainer-like activity on that repo, **or**
- Public membership in the `OWNER` org (when `OWNER` is an org) with
  maintainer/role evidence for this repo

Otherwise **no** — including automation posters, random commenters, and
`author_association: NONE` triage bots even if they comment often. Use the
activity grid + totals as supporting evidence, not as sole proof of
maintainer status (high comment volume alone ≠ maintainer).

Heuristics for **Is bot: yes**:

- GitHub user `type == "Bot"`, **or**
- Login contains `[bot]` / is a GitHub App installation actor, **or**
- Clear automation-only poster (Codex connector, changeset-bot, graph/sweeper
  triage bots, etc.)

Otherwise **Is bot: no**.

## Step 3 — HENRY email design (mandatory template)

**The email body MUST come from the Henry skill email template.** Do not invent a
layout and do not use any Ono-local HTML shell.

**Source of truth (always):**

`~/.claude/skills/henry/templates/email-dark.html`

Also read before filling:

`~/.claude/skills/henry/SKILL.md` → **Format adapters → Email**

That template is inline-table (tables + inline hex) and subject-agnostic (slots only).
Ono fills the slots with report content — it does not own or fork the shell.

### Hard rules

- **Copy `~/.claude/skills/henry/templates/email-dark.html` verbatim** as the outer
  shell. Fill every `{{…}}` placeholder. Keep bar, collage hero, reading column,
  inline stage, three hot-block sections (header only; body **under** the block),
  and footer. Do not redesign.
- Copy Henry `elements/` beside the filled HTML for local preview
  (`../elements/…`). **Before delivery**, rewrite every Henry collage `<img src>`
  to a **resized data-URI** (proven) or absolute https — relative paths break
  in the filled HTML. Rewrite the commenter avatar the same way (or keep a stable
  `https://avatars.githubusercontent.com/…` URL) and tag it
  `data-ono-avatar="1"` only.
- **Do not** use `email-template.md` or any light bone “report” layout as the shell.
- **Do not** ship a stripped/minified alternate design, a plain SaaS card, or a
  “compact” rewrite that drops Henry structure.
- Hot accent block = **header only**. Body copy sits under the colored row, never
  inside the fill. No vermilion pull-quote. No TOC.
- Reversed headline word must be **inline styles** (do not rely on CSS classes):
  `<span style="background:#AEE81A;color:#0A0A0A;padding:0 6px 1px;">WORD</span>`
- If size is a concern: compress the **activity grid** and/or resize collage
  assets — never gut Henry chrome or the three sec blocks.
- No emojis in the body.
- Title line:
  `WRK Reviewer Ono · <repo>#<n> · @<handle> · <legitimate|partial|not|unclear>`

### Map Ono report → Henry placeholders

| Henry slot | Ono content |
|---|---|
| `{{PREHEADER}}` | Same gist as the title line (short) |
| `{{BRAND}}` | `WRK REVIEWER ONO` |
| `{{META}}` | `REPO#N · @handle · MAINTAINER YES/NO · BOT YES/NO` |
| `{{KICKER}}` | Verdict label (`LEGITIMATE` / `PARTIAL` / `NOT LEGITIMATE` / `UNCLEAR`) |
| `{{HEADLINE}}` | `@handle on #N` (`<br />` + lime reverse span as needed) |
| `{{HERO_STANDFIRST}}` | One-line subhead (what the commenter pushed) |
| `{{COLLAGE_TAG}}` | Short mono credit, e.g. `[ 01 / 12 ] Ink figure · [ Lime ] Halftone` |
| `{{STANDFIRST}}` | Overall verdict + `Is maintainer` / `Is bot` (yes/no) |
| `{{BODY}}` | Recommended action (short) |
| `{{INLINE_CAP}}` | e.g. `[ Fig. 01 ] Ink figure · inline` |
| `{{SECTION_1_LABEL}}` / `{{SECTION_1_TITLE}}` / `{{SECTION_1_BODY}}` | `01` / Issue recap / bullets |
| `{{SECTION_2_LABEL}}` / `{{SECTION_2_TITLE}}` / `{{SECTION_2_BODY}}` | `02` / What they said + legitimacy (wrk-rev-com) |
| `{{SECTION_3_LABEL}}` / `{{SECTION_3_TITLE}}` / `{{SECTION_3_BODY}}` | `03` / Who is the commenter (avatar + bullets + activity grid + Is maintainer / Is bot / Repo maintainer) |
| `{{FOOTER_LEFT}}` | `Generated by wrk-reviewer-ono · <UTC>` |
| `{{FOOTER_RIGHT}}` | Source comment/PR URL |

## Step 3b — Assert Henry elements

After rewriting every Henry collage `<img src>` (with `data-henry-element`) and
embedding the commenter avatar (`data-ono-avatar="1"`), write the HTML to a temp
file and run:

```bash
python3 ~/.claude/skills/wrk-reviewer-ono/scripts/assert_henry_elements.py /tmp/ono-report.html
```

**Hard gate:** if exit code ≠ 0, fix the HTML and re-run before treating the
report as done.

On success, stdout includes:

- `ONO_HENRY_ELEMENTS_OK=1`
- `ELEMENTS_USED: atmospheres/glow-blue.png, …`
- `ONO_HENRY_ELEMENTS_JSON={…}`

Keep the `ELEMENTS_USED` line for the chat reply.

## Step 4 — Deliver

1. Fill Henry from `~/.claude/skills/henry/templates/email-dark.html`.
2. Rewrite collage `<img src>` to resized data-URIs or https. Set
   `data-henry-element` on each Henry img. Avatar uses `data-ono-avatar="1"` only.
3. Assert (Step 3b). Do not finish on failure.
4. Reply in chat (required). Write `tmp/wrk-reviewer-ono-<repo>-<n>.html` only
   if the user asked for an HTML copy.
5. Do **not** send mail. Do **not** call a mail MCP.

---

## Chat reply

Keep it short:

1. Verdict + `Is maintainer: yes|no` + `Is bot: yes|no` (and Repo maintainer)
2. Whether the commenter’s ask should be acted on
3. HTML path if they asked for a file; otherwise say the report is in-chat only
4. `ELEMENTS_USED: …` (from assert_henry_elements.py)

Do not paste the full HTML into chat unless asked.
